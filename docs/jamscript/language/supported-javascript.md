# Supported JavaScript in JamScript

There are two related but different questions:

1. Can ScriptC compile a JavaScript construct in an isolated language test?
2. Can the current JamScript M2 runtime encode it at an action or state
   boundary?

Passing the first test does not automatically make a value a portable ABI
type.

## Language core

| Feature | Current status | Notes |
|---|---|---|
| `const` / `let` | Supported | Used by the service fixtures. |
| Functions and helpers | Supported | Helper functions can be called from action bodies. |
| `if`, `for`, `while` | Supported | Covered by ScriptC conformance fixtures. |
| Arithmetic, comparisons, boolean logic | Supported | Keep values within the declared type/range. |
| Object literals and property access | Supported | Useful for records and local computation. |
| Arrays and `Uint8Array` | Supported in ScriptC conformance | They are not automatically ABI arrays. |
| Strings | Supported in isolated ScriptC conformance | Current M2 boundary encoding does not execute `string(N)` yet. |
| Closures and classes | No compatibility promise | Do not make them part of a portable Service contract. |
| `try` / `catch` | Limited | Use `abort(code)` for an application failure; uncaught errors become fatal runtime errors. |

## Current M2 executable boundary

The action/state codec generated by `toolchains/scriptc/m2/compile-service.mjs`
currently supports these types, including nested `record` fields:

```text
unit, bool, u8, u16, u32,
address, fixedBytes(N), bytes(N), record({...})
```

The parser and ABI generator know about more types, including `u64`, `u128`,
signed wide integers, strings, arrays, options, tuples, enums, and results. The
client codec can encode and decode those descriptors, but using them in the
current M2 action/state execution path may fail during the ScriptC transform.
Use the smaller set above for a Service you need to build today.

:::tip Why does `jams new` use `u64`?

The scaffold preserves an older counter-shaped example while the M2 executable
codec is being expanded. `check` and `abi` can validate that scaffold, but a
current buildable example should use `u32` and should persist its result in
managed state, as shown in [Your First Service](../getting-started/first-service.md).

:::

## Deliberately unavailable APIs

The deterministic profile rejects these surfaces:

- `Date`, `Date.now()`, `performance.now()`, and other clocks;
- `Math.random()`, entropy sources, and uncontrolled randomness;
- `process`, environment variables, filesystem, network, sockets, and
  `fetch`;
- timers, `Promise`, `async`/`await`, dynamic `import`, `eval`, `require`, and
  the `Function` constructor;
- DOM, browser globals, and `globalThis`-style ambient access.

The current M2 transform checks the complete source unit, so placing a
forbidden API in an unused helper is not a reliable way to hide it. Remove the
API or move that logic outside the Service.

## Authentication-specific rules

`publicAction()` supplies an empty sender and the current M2 compiler rejects a
public action that reads `ctx.sender`. The current generated runtime supports
either all-wallet actions or exactly one public action; do not mix public and
wallet actions in one Service.

Native C imports are also not part of the current public M2 source path. The
manifest has plumbing for native modules, but the M2 transform currently
accepts imports from `jam` only. Treat `native:<module>` as experimental until
that boundary is enabled end to end.
